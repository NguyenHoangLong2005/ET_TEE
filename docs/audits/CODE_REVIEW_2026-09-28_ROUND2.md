## 1. What I found before touching anything

The user's own work (uncommitted, mixed into the working tree alongside my earlier Phase 1 fixes) is **substantial and largely correct**, verified by direct execution, not by reading commit messages:

- **3 new Flyway migrations**, each with an explicit "checked read-only against real data first" note and the actual numbers found (e.g. "16838/16838 variants have color_hex", "0 orphan support_tickets rows"). This is exactly the evidence discipline the audit asked for.

- **A whole new `StaffMarketingController`/`/api/staff/marketing/**`** — the exact missing namespace from MKT-API-001 — backed by a real `marketing_posts` table and `campaigns.type`/`target_audience` columns, matching the frontend's contract field-for-field.
- **The fabricated analytics page is gone.** `analytics/page.tsx` now has zero hardcoded datasets; it calls the real `since`-aware analytics endpoints, and those endpoints now genuinely honor `since` (previously ignored) and query the DB instead of `.findAll()`-ing the whole table into memory.
- **Voucher usage is now atomically incremented** via a single conditional `UPDATE ... WHERE used_count < max_uses`, with `@Modifying`, closing the race the audit flagged. A `VoucherConcurrencyIntegrationTest` exercises it.
- **The CSKH compensation-voucher leak is closed**: `findAllActive` now excludes rows with `grantedToCustomerId`, and `createVoucher` explicitly nulls that field so marketing can't mint one.
- **The shop-owner approval bypass is closed**: a voucher created with a `shopId` starts `PENDING_APPROVAL`/`isActive=false` unless already `APPROVED`.
- **A real campaign state machine** (`DRAFT→SCHEDULED→ACTIVE→PAUSED→COMPLETED`, with `CANCELLED` reachable from the live states and both terminal) replaced the old "any string accepted" status setter.
- **`Stocktake.shopId`** — the schema gap I flagged in my own Phase 1 report — now has a real migration (`ALTER TABLE ... ADD COLUMN`, backfilled, indexed) and a dedicated `StocktakeShopIsolationIntegrationTest`.
- `out-of-order=true` was added to the Flyway config, closing the baseline-version-floor hazard (DB-001) I'd flagged.
- All the "(Mock)" toasts, fake success states, and demo placeholder copy I found in the original audit are gone from the code I checked.

I'm stating this plainly because the instructions in this conversation repeatedly warn against fake completion in both directions — inventing problems to look thorough is exactly as dishonest as inventing fixes. This work is real, and I verified it by running the suite, not by trusting the diff stat.

## 2. Bugs I found and fixed in this pass

| # | Bug | Evidence | Fix |
|---|---|---|---|
| 1 | **Voucher status had no transition validation** (campaigns got a state machine, vouchers didn't). `PENDING_APPROVAL → ACTIVE` or `REJECTED → ACTIVE` were both silently accepted through `updateVoucherStatus`, bypassing shop-owner approval a second, different way than the one already closed. | `MarketingService.updateVoucherStatus` had no `validateCampaignTransition`-equivalent | Added `validateVoucherTransition`, mirroring the campaign state machine's style: `ACTIVE↔PAUSED`, both → `CANCELLED`/`EXPIRED`; `PENDING_APPROVAL`/`REJECTED`/`CANCELLED`/`EXPIRED` are terminal from this endpoint (approval/rejection stays in `StoreOwnerService`). |
| 2 | **Mass-assignment → cross-record overwrite.** `createVoucher`/`createCampaign`/`createBanner` bind `@RequestBody` directly onto the JPA entity and never clear `id`. Since these are `GenerationType.IDENTITY`, a client-supplied `"id": 5` in the create request makes Spring Data's `save()` treat the entity as "not new" and issue a **merge/UPDATE against voucher/campaign/banner id=5** instead of inserting a new row — a marketing user could silently overwrite an arbitrary existing voucher by guessing its id while appearing to create a new one. | Traced `SimpleJpaRepository.save()` semantics against `@GeneratedValue(strategy = IDENTITY)` + no explicit `isNew()` override | `voucher.setId(null)` / `campaign.setId(null)` / `banner.setId(null)` at the top of each `create*` method, before any other field is touched. Checked the equivalent Supplier/Manufacturer controllers — both already construct a fresh entity server-side and were not affected. |
| 3 | **Dead frontend refresh-token round-trip.** `apiRequest` called `POST /api/auth/refresh` on every 401. No such endpoint exists on the backend (confirmed: `grep -rn "refresh" backend/src/main/java` → 0 hits) and no refresh token is ever issued at login, so this always 404'd before falling through to the same `clearAuthSession()` it would have reached anyway — a wasted network round-trip on every session expiry, and confusing dead code implying a feature that was never built. | `web/src/lib/api-client.ts` | Removed the `refreshAccessToken()` function and the retry branch; 401 now goes straight to `clearAuthSession()`. |
| 4 | **`test_role` cookie/localStorage role override (2 locations).** `proxy.ts`'s edge middleware read a `test_role` cookie and trusted it over the real JWT for routing decisions; `lib/auth.ts#getActiveRole` (used by `PermissionGuard` and the live `StaffSidebar`) read a `test_role` **localStorage** value and trusted it over the account's actual role. Either could be set from the browser console (`document.cookie='test_role=ADMIN'` / `localStorage.setItem('test_role','ADMIN')`). The backend's own authorization was never affected (Spring Security has no knowledge of this cookie), so no data was ever exposed — but a client-settable admin-role switch has no legitimate place in shipped code. | `proxy.ts:106-109` (before fix), `lib/auth.ts:192-196` (before fix) | Removed both; role now always comes from the real JWT/account data. |
| 5 | **Two marketing pages, two API namespaces, two incompatible vocabularies.** `/staff/vouchers` and `/staff/banners` (orphaned duplicates of `/staff/dashboard/marketing/{vouchers,banners}`, unreachable from the real sidebar — confirmed by grepping every live nav config) still called the *old* `/api/marketing/admin/**` endpoints and used `status: "INACTIVE"`, a value that doesn't exist anywhere else in the voucher status vocabulary (`ACTIVE`/`PAUSED`/`PENDING_APPROVAL`/`REJECTED`/`CANCELLED`/`EXPIRED`). Fix #1 above would have made this orphaned page's toggle button silently 400 the moment a stray link reached it. | `staff/vouchers/page.tsx`, `staff/banners/page.tsx`, confirmed orphaned via `grep` over every nav/route config in `web/src/config` and `web/src/components/layout` | Deleted both orphaned pages and the dead `components/staff/StaffSidebar.tsx` they were linked from (unused — the real layout imports `components/layout/StaffSidebar.tsx`). Fixed the one dangling link to `/staff/vouchers` (in the also-largely-orphaned bare `/staff/dashboard` page) to point at the canonical route. Cleaned the now-stale registry entries in `role-navigation.config.ts` and `tier-branding.config.ts`. |
| 6 | **48,000-line dead mock-data file.** `web/src/lib/data/products.ts`, headed `// TODO: Replace with Spring Boot API call`, had zero importers anywhere in the codebase — confirmed by grep. | `src/lib/data/products.ts` | Deleted (and the now-empty `src/lib/data/` directory). |
